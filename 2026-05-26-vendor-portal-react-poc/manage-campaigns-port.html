Vendor Portal React POC - Manage Campaigns Port

Created for the Rails route https://my.g2.test/g2-seller-solutions/ppc. The record tracks implementation work, adjustments from visual review, and integration learnings from porting the Vendor Portal screen into UE.

Open Follow-Up

  • If this approach is accepted, split the compatibility UI primitives into smaller files and add focused Jest coverage for table sorting and draft deletion.
  • Resolve or bypass the current TypeScript 4.6 incompatibility with newer @sinclair/typebox declarations if full tsc validation becomes required.

Realizations

  • UE already had a React + TypeScript Webpack proof point, so the lowest-risk path was to add a sibling entry instead of introducing a new frontend build system.
  • The source route relies on React Router framework APIs plus design-system dependencies such as Radix, TanStack Table, Base UI, and class-variance-authority. Those packages are not currently present in UE.
  • For this POC, preserving the component usage shape mattered more than preserving the exact data-loading implementation, so loader/action responses were modeled as local mocked data and event dispatches.
  • Links to other Vendor Portal routes were intentionally converted into mocked toast interactions so the page stays focused on UI and React behavior.

Learnings

  • Imported UI components can come across as a compatibility layer first, then be swapped for real shared packages later if the POC graduates.
  • Tailwind class names from Vendor Portal do not map one-to-one to UE's stylesheet surface, so the POC injects scoped CSS under vp- classes to approximate the visual layout without global churn.
  • UE's Webpack loader excludes paths containing vendor, so POC source files live under webpack/assets/javascripts/vp_poc even though the bundle remains named vendor_portal_ppc_entry.
  • A future production port should decide between vendoring the design-system dependency graph, publishing shared UI packages, or implementing a more deliberate UE adapter layer.

UE App

UE uses Tailwind ^3.1.8 through tailwindcss/tailwind.config.js and a separate Elevate preset under engines/elevate/tailwind.config.js. Its main custom theme modules are legacy JavaScript token files for colors, padding, margin, font family, line height, radius, shadows, and breakpoints.

Vendor Portal

Vendor Portal uses Tailwind 4.3.0 with a CSS-first theme in app/styles/tailwind.css. Tokens are declared with @theme static, then bridged to older Vendor UI names through vendor-ui-compat-layer.css.

Area Main Difference Impact On This POC
Class generation UE scans ERB/Slim/HTML plus JS/JSX paths. Its current main Tailwind content glob does not include TS/TSX files under webpack/assets/javascripts. Vendor Portal source is TS/TSX-heavy and Tailwind v4-driven. Simply replacing vp- CSS with Tailwind classes inside the POC TSX would not be enough unless UE's Tailwind content config is expanded or the classes already exist elsewhere.
Spacing scale Vendor Portal sets --spacing: 1px, so utilities like gap-24, p-24, and compat classes like p-24px mean 24px. UE's custom spacing is split between padding and margin: p-1 is 24px, but m-1 is 12px, and default Tailwind spacing still applies to generic utilities such as gap-24. Spacing classes are the riskiest direct copy. The POC's vp-gap-24 maps to Vendor Portal intent, but UE's native gap-24 would not mean the same thing without a config change.
Typography Both apps use Figtree, but Vendor Portal defines opinionated text-size-* utilities that bundle font size, line height, margin reset, and text-box trimming. UE mostly has font family, weights, and a smaller line-height scale. Typography should inherit from UE where possible. Directly recreating Vendor Portal's Text utilities caused visible drift earlier, so removing local font overrides was the correct direction.
Color naming Vendor Portal exposes semantic colors such as text-fg-main, text-fg-brand, bg-brand-blue-1, bg-gray-1, and text-link-blue. UE uses older names such as navy, midnight, rorange, success, error, link, and Foundation-like grays. Some values are close, but names and shade numbers are not portable. A small mapping table is safer than copying Vendor Portal color classes directly.
Logical sizing utilities Vendor Portal components use Tailwind v4 logical utilities such as inline-24, block-20, min-block-40, inline-full, and arbitrary logical values. UE's Tailwind v3 setup does not provide the same logical-property utility surface by default. Core controls like buttons, icon buttons, menus, tables, and modals cannot be moved over class-for-class without either rewriting those utilities or using UE-native component styles.
Radius and shadow Vendor Portal uses pixel-named compatibility tokens like rounded-4px, rounded-8px, and shadow-2. UE has its own radius names and different shadow values. Visual matching through UE classes is possible, but exact parity needs either token mapping or accepting UE-native radii/shadows.
Base/reset layer Vendor Portal's base layer resets margins, borders, list styles, and buttons with rules such as button { all: unset; }. UE already has established global layout and vendor-admin styles. Importing Vendor Portal's Tailwind base into UE would be too broad for this POC. Component-level adaptation is safer than bringing the whole Vendor Portal CSS reset.

Current POC CSS Layer Assessment

  • Good candidates to replace with UE/native utilities: basic flex layout, alignment, justify rules, width, text alignment, cursor, disabled opacity, table text alignment, and the page-level padding wrapper.
  • Needs token mapping before replacement: gaps, padding values, status chip colors, link blue, brand text, error text, borders, radii, and shadows.
  • Better solved with UE components or deliberate adapters: table structure, popover/dropdown positioning, modal layout, toast placement, icon button states, and chip semantics.
  • Important blocker: UE's current Tailwind content config should include TS/TSX before relying on Tailwind classes authored in webpack/assets/javascripts/vp_poc.

Recommendation

Do not import Vendor Portal's full Tailwind theme or base reset into UE for this POC. The lower-risk path is to progressively remove local vp- classes where UE already has equivalent behavior, then create a small documented token map for the mismatches. For a real production port, the best long-term outcome is either using UE/Elevate-native components for table, buttons, modal, menu, and toast, or publishing the Vendor Portal core UI primitives with their required Tailwind v4 token contract as an explicit dependency.
