CSS and styling landscape

UE is running several styling systems in parallel

The dominant layer is a global Sass bundle called nessy_app, but it now coexists with Tailwind, legacy atomics, Foundation, Elevate, engine-local Sprockets CSS, vendor styles, and a small React Emotion surface.

Executive Summary

The app is not on a single styling architecture. It is a layered compatibility system where global Sass, Foundation, Tailwind, and Elevate all share the same markup surface.

Primary Layer

webpack/assets/stylesheets/nessy_app.scss is the main public stylesheet. It imports Tailwind, Foundation, vendor CSS, core styles, forms, and hundreds of component partials.

Migration Direction

Elevate is the newer design-system direction. It uses elv- utilities and component classes, but it explicitly coexists with Nessy rather than replacing it.

Main Risk

Changing or removing nessy_app, Foundation, or the legacy atomic compatibility classes has high blast radius because templates mix all of those class families.

Switching Constraint

Any layer switch must be route-by-route or component-by-component. A broad rewrite would cross Sass, PostCSS, Rails layouts, engine assets, JS widgets, and CSS-in-JS styles.

Tailwind Upgrade Scope

The upgrade objective is Tailwind v4 implemented without disrupting the current UE setup. The candidate paths are Elevate-first, a shared Tailwind 3.4.x stepping stone, a scoped v4 bundle, or a direct main UE upgrade if proven safe.

Upgrade Difficulty

Tailwind v4 is a tooling and browser-support migration. UE currently embeds Tailwind inside a Sass-first Gulp pipeline, which is the central compatibility risk.

Tailwind Upgrade Implications

This section narrows the research to the ticket objective: upgrading the current Tailwind layer. It does not assume a styling-layer replacement.

Current Main Version

package.json has tailwindcss: ^3.1.8. The main Tailwind config is tailwindcss/tailwind.config.js.

Current Latest Version

npm view tailwindcss version and npm view @tailwindcss/postcss version returned 4.3.0 on 2026-06-03.

Elevate Is Separate

engines/elevate/package.json has tailwindcss: ^3.4.10 and uses its own engines/elevate/tailwind.config.js, PostCSS config, Rsbuild pipeline, and elv- conventions.

Browser Support Gate

UE has .browserslistrc set to last 2 versions. Tailwind v4 requires a stricter modern-browser baseline, so analytics/product support policy should be confirmed before implementation.

What Changes In Tailwind v4

Change UE implication Risk
PostCSS integration moved from tailwindcss to @tailwindcss/postcss. gulpfile.js currently calls tailwindcss(config.tailwind.config) inside gulp-postcss. That cannot be a blind package bump. High
Tailwind v4 uses @import "tailwindcss" rather than v3-style @tailwind directives, and it changes the recommended import/config model. nessy_app.scss currently imports tailwindcss/base, tailwindcss/components, and tailwindcss/utilities from inside SCSS. High
Tailwind v4 is not designed for Sass/Less/Stylus preprocessing. UE's main CSS pipeline is Sass-first. Tailwind is mixed into nessy_app.scss before hundreds of Sass partials and vendor imports. High
JavaScript config is still possible for compatibility, but v4 prefers CSS-first configuration. UE has substantial JS config in tailwindcss/*.js, including colors, spacing, breakpoints, and a custom nessyPlugin. Medium
Browser support is Safari 16.4+, Chrome 111+, and Firefox 128+. Public G2 pages may have a broader browser profile than internal seller/admin pages. This must be checked against traffic before upgrading the shared nessy_app bundle. High
Some deprecated utilities were removed or renamed, and several defaults changed. UE contains many generated compatibility utilities, arbitrary values, opacity utilities, shadow/radius utilities, and dynamic class comments. Medium

UE-Specific Upgrade Surface

  • package.json: main app currently has tailwindcss ^3.1.8, postcss ^8.5.13, postcss-import ^15.0.0, autoprefixer 10.4.4, gulp-postcss 9.0.1, and sass 1.32.12.
  • gulpfile.js: main Tailwind runs as one PostCSS plugin after Dart Sass compilation, with postcss-import, tailwindcss/nesting, Tailwind, Autoprefixer, and Flexibility.
  • tailwindcss/tailwind.config.js: content includes app views/components, engines, Webpack JS/JSX, Storybook docs, and packs.
  • tailwindcss/nessy.plugin.js: custom utilities generate c-*, bg-*-hover, and legacy order aliases from theme colors/screens.
  • webpack/assets/stylesheets/tailwind: 24 custom Tailwind component/utility SCSS files using @layer and @apply.
  • webpack/assets/stylesheets/components: regular Sass component files also use Tailwind @apply, so Tailwind is not isolated to the tailwind/ folder.

Likely Implementation Paths

Path What it means Pros Cons
Elevate-first Tailwind v4 Upgrade engines/elevate to Tailwind v4 while leaving the main nessy_app Tailwind output unchanged. Best isolation if migrated USE/React work can live behind Elevate assets and elv- conventions. Does not modernize main UE utilities; still needs proof that Elevate's Rsbuild/PostCSS/import model works cleanly with v4.
Common Tailwind 3.4.x stepping stone Move main UE from ^3.1.8 to the same 3.4.x baseline as Elevate before attempting v4. Lower-risk modernization step; keeps the Sass/PostCSS model; exposes deprecated/custom utility problems before the v4 jump. Does not satisfy "latest"; may not unblock components that require v4-specific classes.
Split Tailwind into a CSS-first entrypoint Build Tailwind v4 from a plain CSS entrypoint and keep Sass for Nessy/Foundation separately. Aligns better with Tailwind v4's intended workflow. Requires careful CSS load-order design and may expose specificity/order regressions.
Route-scoped v4 pilot Add a v4 Tailwind bundle for the migrated component surface only, before changing global nessy_app. Best blast-radius control for DMVPC component migration. Risks duplicate Preflight/base styles or conflicting utility definitions unless scoped carefully.
Direct main UE v4 upgrade Install tailwindcss and @tailwindcss/postcss v4 in the main app, update Gulp/PostCSS integration, then resolve breakages. Most direct path if the current Sass/Gulp pipeline can be made compatible. Highest uncertainty because Tailwind v4 is not designed for Sass preprocessing and UE imports Tailwind from SCSS.

Current recommendation: do not describe this as a simple dependency bump. Use a spike to choose between Elevate-first v4, a shared 3.4.x stepping stone, a scoped v4 bundle, or direct main UE v4. The implementation ticket should be written only after that scenario is selected.

Risk Register

Risk Severity Why It Matters Mitigation
Replacing nessy_app broadly High It is the default public CSS bundle and contains Tailwind, Foundation, vendor CSS, core styles, forms, and most local components. Do not replace globally. Introduce isolated route/component boundaries and measure visual diffs route-by-route.
Removing Foundation or changing Foundation settings High Foundation classes appear across templates, Sass variables depend on its palette/settings, and JS widgets import Foundation for accordion, dropdown, popover, and Magellan behavior. Inventory component-by-component. Keep a compatibility stylesheet until all markup and widget behavior moves.
Changing Tailwind config, prefixing, or content paths High The main app uses unprefixed Tailwind plus compatibility aliases. Dynamic-class comments already exist, which means purge/content scans can miss runtime classes. Add safelist tests for known dynamic classes and keep compatibility aliases during migration.
Upgrading Tailwind v3 to v4 inside the existing Sass/Gulp pipeline High Tailwind v4 changes the PostCSS plugin package, import model, browser support baseline, and Sass compatibility assumptions. Run a dedicated spike before committing to direct v4. Prove build output and visual smoke pages before widening scope.
Unsupported browser regressions after v4 High Tailwind v4 depends on modern CSS features and has a stricter browser floor than UE's current last 2 versions Browserslist policy implies. Check production browser analytics for affected public and seller-admin surfaces before upgrading the shared bundle.
Confusing main Tailwind with Elevate Tailwind High Main Tailwind is configured under tailwindcss/ and currently depends on Tailwind 3.1.x. Elevate has its own Tailwind 3.4.x preset and elv- conventions. Treat them as separate systems unless an explicit consolidation plan handles prefixes, versions, and content paths.
Dropping legacy atomic aliases High Storybook calls several atomics backward-compatibility support, but extracted utility usage is broad. Many templates still mix old aliases and Tailwind defaults. Deprecate by codemod and lint, not by deletion. Track alias usage before removing generated classes.
Elevate asset manifest failure Medium elevate_asset_tags rescues manifest load errors and returns no tags. In development/test, missing Elevate build output can silently remove Elevate CSS. Add smoke checks for pages that require Elevate assets and document the elevate:dev/elevate:build dependency.
Emotion styles bypassing global migration Medium React components with css={...} will not be affected by Sass/Tailwind cleanup. Some combine Emotion with utility classes. Track CSS-in-JS as a separate migration lane for React surfaces.
Weak lint enforcement Medium Stylelint config exists, but the GitHub workflow action appears commented. Selector discipline may depend on local convention rather than CI. Re-enable or replace style linting before large styling migrations.
Vendor CSS override regressions Medium Quill, Dragula, Swiper, Notyf, Flatpickr, Spectrum, Select2, and ActiveAdmin styles are imported or overridden in multiple places. Keep vendor imports explicit and verify affected widgets visually after bundle/order changes.

Recommendations

  • Define the desired target per surface. Public marketplace, MyG2/vendor-admin, embedded widgets, ActiveAdmin, and Elevate should not necessarily use the same short-term migration path.
  • Treat Elevate as additive first. The current code and docs describe coexistence with Nessy, not a wholesale replacement.
  • Protect compatibility utilities. Before removing atomics or changing Tailwind aliases, build a usage report that maps old classes to replacement classes.
  • Add visual smoke coverage around CSS bundles. Start with one route for nessy_app, one MyG2/vendor-admin route, one embedded grid, one Elevate route, and one ActiveAdmin route.
  • Revisit Stylelint and selector validation. If styling migration is coming, CI should enforce the conventions before the migration starts.
  • Separate build-pipeline work from design-system work. Moving from Gulp/Sass to another build tool is a different risk than moving from Nessy/Foundation classes to Elevate classes.
