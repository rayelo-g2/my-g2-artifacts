Architecture Decision Record

ADR 0002: Core Components Migration

Define the reuse and mapping strategy for shared UI primitives used by migrated G2DM views inside MyG2.

StatusDraft for ticket alignment
Date2026-06-03
ProjectUnified Seller Experience

Context

ADR 0001 establishes that relevant G2DM React views will be mounted inside MyG2 Rails pages. Those views currently depend on shared UI components and visual patterns. The Unified Seller Experience should not preserve the current G2DM UI exactly; the migrated views should feel consistent with MyG2 and Elevate.

This creates a dedicated component workstream: identify the core components needed by the first migrated routes, map those usages to existing reusable components, create one implementation subtask per component, and document any functional gaps that need separate follow-up.

Decision

Core component migration should be treated as a reuse and mapping task. The components needed by the first migrated routes should be reused rather than created as part of this ticket.

  • Inventory the core components needed by the first migrated routes.
  • Map each G2DM component usage to the existing reusable component or Elevate reference that should cover it.
  • Create one subtask per component to be migrated or validated for reuse.
  • Reuse existing components for the migration work in this ticket.
  • Keep core UI components presentational: they should receive props and callbacks, not own Rails data fetching or mutations.
  • Use MyG2/Elevate consistency as the visual target, not pixel parity with the current G2DM Vendor Portal.

Important distinction: if the mapping exposes missing shared behavior in existing Elevate components, that should be tracked as separate component enhancement work. It is out of scope for this ticket.

Scope

In scope Out of scope
Inventory of shared UI primitives used by migrated G2DM views, such as buttons, inputs, selects, checkboxes, tabs, tables, empty states, alerts, modals, layout primitives, and similar reusable controls. Route-specific feature implementation, business logic, Rails endpoint design, data loading, mutations, and authorization/session behavior.
Mapping each required component usage to the existing reusable component or Elevate reference that should cover it. Strict visual parity with the current G2DM Vendor Portal UI when that conflicts with MyG2/Elevate consistency.
Validation that existing reusable components render correctly inside the MyG2 React-in-Rails mounting environment. Creating new React components or modifying existing Elevate components as part of this ticket.
Documenting functionality gaps discovered during mapping. Implementing those gaps; they should be handled by separate follow-up tickets when needed.

Migration Method

Step Output Notes
Audit List of core component usages required by the first migration candidates. Start from concrete routes instead of trying to migrate every possible component upfront.
Map Component mapping table: G2DM usage, existing reusable component, Elevate reference, functionality notes, status. No action column is needed because the migration path for this ticket is reuse. Gaps should be captured as notes or follow-up tickets.
Split One Jira subtask per component to be migrated or validated for reuse. Each subtask should point back to the mapping table and be independently reviewable.
Validate Existing components render correctly in the React-in-Rails environment. Components should stay reusable and data-agnostic.
Review Visual and behavioral review against MyG2/Elevate expectations. Review should identify gaps, but gap implementation is out of scope for this ticket.
Adopt First migrated route using the reused component set. The first route should prove the reused components work in the React-in-Rails architecture.

Acceptance Criteria for Component Work

  • A scoped component inventory exists for the first migration candidates.
  • Each component usage has a documented mapping to an existing reusable component, Elevate reference, functionality notes, and status.
  • One Jira subtask exists per component to be migrated or validated for reuse.
  • Each component subtask is independently reviewable and references the relevant mapping entry.
  • Existing reusable components render correctly inside the MyG2 React-in-Rails mounting environment.
  • Components match MyG2/Elevate visual direction and expected behavior for equivalent controls.
  • Components are reusable and data-agnostic: no Rails endpoint calls, authorization checks, or route-specific data loading inside core UI components.
  • Route-specific logic remains in the migrated view/container layer or Rails backend layer, not in shared primitives.
  • Any missing functionality or Elevate component enhancement need is documented as follow-up work outside this ticket.
  • UX/design review confirms the reused components are ready to be used by migrated routes or identifies follow-up gaps.

Relationship to Data Layer Work

The data layer POC is important for migrated routes and views, but it should not be a blocker for purely presentational core component work. Shared UI components should be able to render from props and emit callbacks without knowing how the Rails data layer is implemented.

Once the first migrated route is assembled, that route should validate both concerns together: Rails-owned data and actions feeding React views that use the reused component set.

Consequences

Positive

  • Keeps the component work focused on inventory, mapping, and reuse rather than route-specific feature work.
  • Prevents accidental coupling between shared UI primitives and Rails data-fetching patterns.
  • Surfaces any Elevate functionality gaps early without absorbing that implementation into this ticket.

Tradeoffs

  • Some required behavior may need separate Elevate component enhancement work.
  • Component parity requires UX/design review, not only engineering validation.
  • The component inventory should be route-driven to avoid spending time on components that are not needed for the October migration target.

Ticket Implications

A Jira ticket for this work should avoid saying that components are migrated into the Rails-based Elevate design system or connected to the data layer. More accurate phrasing is:

  • Define the core component inventory required for early G2DM route migrations.
  • Map each component usage to the existing reusable component and related Elevate visual/behavioral reference.
  • Open one subtask per component to be migrated or validated for reuse.
  • Reuse existing components for the migration work in this ticket.
  • Keep shared components data-agnostic; data integration belongs to views/containers and Rails-owned endpoints.
  • Document any missing shared behavior or Elevate component enhancement as follow-up work outside this ticket.
  • Validate visual and behavioral alignment against MyG2/Elevate, not strict parity with current G2DM.
