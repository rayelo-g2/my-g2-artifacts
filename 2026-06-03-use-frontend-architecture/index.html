Unified Seller Experience

Frontend Architecture Report

A living architecture hub for the USE frontend migration: the agreed direction, the current boundaries, and the ADRs that will capture decisions as the project evolves.

Summary

The current frontend architecture decision is to host the Unified Seller Experience in MyG2, reuse relevant G2DM React views where practical, and let Rails own routing, authorization, session handling, data loading, and backend actions.

G2DM is the existing Vendor Portal / UVP experience. MyG2 is the Rails application where the unified seller experience will live. The project target is to complete the main migration work by October, with November acting as the external deadline and launch-readiness buffer.

Working principle: reuse the G2DM React implementation to move faster, but adapt the experience to MyG2 and Elevate rather than preserving the current G2DM UI exactly.

Current Decision

The selected approach is React-in-Rails for migrated seller surfaces:

  • Rails routes define the navigational boundary for migrated MyG2 pages.
  • Rails controllers and Rails-side patterns own authorization, session handling, data loading, and mutations/actions.
  • React views migrated from G2DM are mounted inside Rails-rendered MyG2 page shells.
  • Core component usages are mapped to existing reusable components and validated against Elevate visual style and expected behavior.
  • React is used primarily for reuse and delivery speed, not because every screen needs advanced client-side reactivity.

Architecture Boundaries

Rails Owns

  • Routing and page entry points.
  • Authentication, authorization, and session behavior.
  • Data access, loading, and mutation endpoints.
  • Server-side business rules and integration with existing MyG2 patterns.

React Owns

  • Migrated G2DM view rendering inside the page shell.
  • Interactive UI state local to a mounted view.
  • Composition of reused components inside migrated G2DM views.
  • Client-side calls into Rails-owned endpoints.

Elevate Guides

  • Visual style for seller-facing UI.
  • Expected component behavior and interaction patterns.
  • Accessibility expectations for shared controls.
  • Consistency with the broader MyG2 experience.

Not the Goal

  • Rebuilding every G2DM surface as Rails views by default.
  • Moving MyG2 wholesale into G2DM / UVP.
  • Introducing React Router as the primary route owner for migrated MyG2 pages.
  • Preserving the current G2DM UI as the visual target.

Request Flow

The intended flow keeps Rails as the integration boundary and lets React focus on rendering the migrated experience.

User request
    |
    v
MyG2 Rails route
    |
    v
Rails controller / backend layer
    - authorization
    - session handling
    - data loading
    - mutations / actions
    |
    v
Rails-rendered MyG2 page shell
    |
    v
Mounted React view migrated from G2DM
    |
    v
Reused core components
    - mapped to existing reusable components
    - validated against Elevate visual style and expected behavior

Current Workstreams

Workstream Purpose Current Framing
Data layer POC Validate how mounted React views call Rails endpoints for fetch and submit flows. This unblocks route/view migration. It should not be treated as a dependency for purely presentational core UI components.
Component reuse mapping Identify core component usages and map them to existing reusable components and Elevate references. This ticket should validate reuse and document gaps. Modifying existing Elevate components is separate follow-up work.
Route migration Move selected G2DM routes into MyG2 using Rails routing and mounted React views. PPC and PPL are likely early candidates; dashboard, reviews, badges, and listings need product/UX decisions first.
Tracking migration Ensure migrated React-in-Rails surfaces fire the correct G2 tracking events. Tracking validation should be part of migrated route acceptance criteria where user behavior is instrumented.

Open Questions

Area Question Concrete next step
Feature synchronization How do G2DM and MyG2 stay aligned while product teams continue shipping new work? Define the synchronization rule for new work during migration.
Cutoff planning When should teams stop building only in G2DM and start requiring MyG2 implementation too? Produce a cutoff proposal for G2DM-only, dual-build, and MyG2-first work.
Migration sequencing Which routes should move first, and which should wait because they are actively changing? Create a route migration candidate list marked as move now, wait, or needs discovery.
Merged experiences What should happen with dashboard, reviews, badges, and listings? Document product and UX decisions required before those areas enter migration planning.
Component parity How do reused components and Rails Elevate references stay visually and functionally aligned? Define a reuse validation checklist covering style, behavior, accessibility, and any follow-up Elevate component gaps.
Authorization/session integration Which Rails-side patterns should be used for permissions, session handling, and route-level access? Validate the expected Rails integration pattern on the first migrated route.
