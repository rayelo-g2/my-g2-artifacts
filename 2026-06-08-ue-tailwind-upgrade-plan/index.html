UE Tailwind upgrade plan

Move to Tailwind v4 iteratively, with v3 unification first

The safest path is to align UE main Tailwind, UE's embedded Elevate workspace, and the standalone Elevate package on the latest Tailwind v3 line first, then evaluate Tailwind v4 from a stable baseline while touching as little of Nessy, Foundation, Sass, and existing load order as possible.

Summary

This plan turns the styling-landscape research into an implementation sequence for ue-unify-tailwind-3 and the follow-up v4 work. Phase 1 is implemented, validated, merged, and deployed through PR #40142; the standalone @g2crowd/elevate package v3 alignment merged through PR g2crowd/elevate-g2#50 under DMVPC-1837. The first v4 slice is now in code review through Elevate PR g2crowd/elevate-g2#55 and UE consumer PR g2crowd/ue#40359.

First Move

Upgrade the UE Tailwind surfaces and the standalone Elevate package to latest v3, currently 3.4.19, without changing the surrounding styling architecture.

Why First

Main UE started on ^3.1.8. UE's embedded Elevate workspace and the standalone elevate-g2/ checkout started on ^3.4.10. Aligning all of them removes version drift before introducing Tailwind v4's larger build-model changes.

Migration Shape

Keep the current Sass, Gulp, PostCSS, Foundation, Nessy, and Elevate asset boundaries intact during the v3 unification PR.

v4 Constraint

The first v4 move is Elevate-first. Elevate v2.0.0 is published and the UE consumer PR validates the stable package while keeping global nessy_app on v3.

Tailwind v3 Unification Approach

Unification means both Yarn workspaces resolve the same Tailwind package version. It does not mean merging the main UE and Elevate configs, CSS entrypoints, or generated bundles.

Implemented and merged: Phase 1 pins root UE and UE's embedded Elevate workspace to exact 3.4.19 for a deterministic baseline. The standalone elevate-g2/ package follows the same exact baseline on a separate package branch under DMVPC-1837; PR g2crowd/elevate-g2#50 is merged.

DMVPC-1839 — v4 Migration Path Decision

Decision spike (issue G-12). Goal: pick the lowest-risk Tailwind v4 path from the stable 3.4.19 baseline, grounded in the confirmed producer/consumer package model. Evidence gathered 2026-06-12 against the real checkouts.

Recommendation

Elevate-first v4, via a CSS-first @theme / @plugin port of the Elevate preset — not a lift-and-shift of the v3 JS preset. Sequence the work as an elevate-g2 PR (v4-ready republish of @g2crowd/elevate) followed by a UE engines/elevate consumer bump. nessy_app moves to v4 as a separate, later slice. Reject the “direct main UE upgrade first” path and the “scoped route-specific v4 bundle” path for the reasons in the comparison below.

Why the JS preset cannot survive v4 as-is

The v3 contract in elevate-g2/src/tailwind.config.js is built from three v3-only mechanisms, each of which changes form in v4:

v3 contract (today)v4 reality (verified)
prefix: 'elv-' — literal string prefix concatenated onto class names (elv-flex). v4 moves prefix to @import "tailwindcss" prefix(elv); and applies it as a variant (elv:flex), not a literal elv- string. Every existing elv- class in shipped markup/components would need re-emitting. This is the single largest break.
tailwindcss-scoped-preflight via isolationStrategy: isolateInsideOfContainer('[elv]') (JS helper import). Plugin survives — it has a v4 line (4.0.6, dist-tag latest, peer tailwindcss: ^4). But the isolateInsideOfContainer helper is no longer exported; v4 uses a CSS-first @plugin form (isolation-strategy: inside; selector: [elv];). Custom isolation-strategy functions are explicitly “not available in v4.” The exact current call breaks; the intent ports cleanly.
Whole-theme override map (colors, spacing, radii, type scale) in a JS theme: {} object, consumed by UE via presets: [require('@g2crowd/elevate/tailwind')]. v4 is CSS-first: tokens belong in @theme custom properties. The JS-preset consumption pattern is deprecated. research-hub already proves the replacement: it runs v4 and hand-ports the Elevate palette into :root/@theme inline custom properties, and its @g2crowd/elevate dependency is vestigial (no JS import, no elv- classes, not even installed).
Build: PostCSS CLI + tailwindcss/nesting + autoprefixer; source uses @import 'tailwindcss/base|components|utilities'. v4 build is @tailwindcss/postcss (or the Vite/CLI engine) with a single @import "tailwindcss"; nesting/autoprefixer are built in. The elevate-g2 build pipeline must be rewired, not just version-bumped.

Net verdict: the preset semantics survive (tokens, dark mode, scoped preflight intent all expressible in v4), but the delivery mechanism does not. Elevate-first v4 concretely means re-authoring the preset as a v4 CSS-first @theme + @plugin stylesheet and republishing, exactly the shape research-hub validates — it is a re-expression, not a lift-and-shift.

Path comparison

PathVerdictRationale
Elevate-first v4 (CSS-first token/preflight port, republish, then UE bump) Recommended Matches the producer/consumer model: the preset is the shared contract, so it must be v4-ready before any consumer can move. Proven workable by research-hub. Keeps the blast radius inside the package boundary and lets UE adopt on its own schedule via the peer-controlled version bump. Splits naturally into one elevate-g2 PR + one UE consumer PR.
Scoped / route-specific v4 bundle Reject Shared web-style routes (web_style/core.html.slim and others) load nessy_app CSS and Elevate application.css together platform-wide. A scoped v4 bundle would create a third Tailwind runtime overlapping the existing two, multiplying preflight/reset and prefix-collision risk for no durable payoff.
Direct main UE nessy_app v4 first Reject (as the first move) nessy_app has no Elevate preset and an unprefixed global utility surface, so a v4 reset/preflight change there is the highest-overlap, hardest-to-isolate change against shared routes. It should be the last slice, after Elevate is v4 and the shared-route behavior is understood. It is on the roadmap, not the entry point.

Affected surfaces for the recommended path

  • elevate-g2 (producer): package.json (bump tailwindcss peer to ^4, dev to ^4, tailwindcss-scoped-preflight ^3 → ^4, drop tailwindcss/nesting+autoprefixer if redundant); src/tailwind.config.js → CSS-first @theme/@plugin stylesheet (preset re-authored); PostCSS config → @tailwindcss/postcss; source CSS @import 'tailwindcss/...' → @import "tailwindcss" prefix(elv); the ./tailwind export + dist/elevate.css/dist/components.css outputs; version bump + publish of @g2crowd/elevate.
  • UE engines/elevate (consumer): bump @g2crowd/elevate to the new v4 release; replace presets: [require('@g2crowd/elevate/tailwind')] JS-preset wiring with the v4 CSS-first import; bump pinned tailwindcss to 4.x (this consumer controls the resolved peer); rewire its PostCSS to @tailwindcss/postcss; update application.css import of @g2crowd/elevate/dist/components.css.
  • UE nessy_app: untouched in this slice; tracked as a later, separate v4 slice.
  • research-hub: no work; reference data point only.

Shared-route / load-order implications

Because web_style/core.html.slim (plus roi_report_pdf_layout and several Elevate engine layouts) load both stylesheets together, the v4 Elevate bundle must preserve the [elv]-scoped preflight isolation so it does not reset nessy_app-styled DOM. The v4 @plugin isolation-strategy: inside; selector: [elv]; is the direct equivalent of today's isolateInsideOfContainer('[elv]') and must be validated against the runtime-overlap fixture before the consumer bump merges.

Browser-support note

Tailwind v4 targets modern browsers (Safari 16.4+, Chrome 111+, Firefox 128+) and uses native cascade layers / @property / color-mix(). Confirm this clears the UE supported-browser matrix before the consumer bump; if older browsers are still in support, that is a gating constraint on the UE slice (not the elevate-g2 publish).

Delivery slices (feeds G-13)

  1. Slice A — elevate-g2 v4 republish: re-author preset as v4 CSS-first @theme/@plugin, rewire build, bump peer/dev deps, publish a new @g2crowd/elevate. Verify dist/elevate.css/dist/components.css render parity and that scoped preflight still isolates to [elv].
  2. Slice B — UE engines/elevate consumer bump: adopt the new release, move to v4 import + @tailwindcss/postcss, validate against the shared-route runtime-overlap fixture and the smoke matrix.
  3. Slice C (later, separate) — nessy_app v4: only after A+B are stable and shared-route behavior is proven.

Slices A and B are the “more than one delivery slice” the acceptance criteria anticipated, and map onto the G-13 implementation issue.

Migration Principles

  • Touch the styling stack as little as possible. The v3 unification PR should not refactor Nessy, Foundation, Sass partials, asset loading, or CSS architecture unless a Tailwind v3 compatibility issue forces a local change.
  • Separate version alignment from v4 migration. Tailwind 3.4.19 should land as its own reviewable change before any Tailwind v4 package or pipeline work.
  • Keep main UE and Elevate distinct. The first goal is version parity, not collapsing Tailwind configs, prefixes, or asset entrypoints.
  • Prefer evidence over broad assumptions. Each phase should have build output, smoke routes, and a narrow regression read before moving to the next phase.
