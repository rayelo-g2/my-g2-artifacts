Feasibility report

Porting a Vendor Portal React route into MyG2 Admin

This report documents what the Manage Campaigns POC proved, where it needed adaptation, and what future agents or engineers should check before moving production routes between G2DM and MyG2.

Follow-ups

These are the decisions that matter most before moving from a fast rendering proof to a production-quality migration path.

  • Choose the component strategy. Decide whether migrated routes should use UE-native components, a temporary compatibility layer, or published Vendor Portal UI packages.
  • Close the dependency gap. Choose a plan for React 17 versus React 19, Tailwind 3 versus Tailwind 4, React Router, and TypeScript before the next migration attempt.
  • Define the data boundary. Decide how Vendor Portal loader/action patterns should move into Rails-based data handling.
  • Document style ownership. Build a Tailwind and design-token map so React-based routes do not drift away from Rails views.
  • Compare the direction. Revisit the inverse option of moving MyG2 features into Vendor Portal before scaling route work.

Executive Summary

The POC proves one narrow but important point: Vendor Portal React components can render inside the Rails-based MyG2 Admin app at a fast pace. Mocked data, a dedicated Webpack entry, and a scoped compatibility layer were enough to paint the Manage Campaigns route and preserve core interactions.

It does not prove that production migration is copy-paste. The largest gaps are framework version drift, React Router loader/action expectations, Tailwind token differences, and duplicated UI primitives. The next iteration should convert those gaps into explicit migration decisions.

Feasibility

High for isolated UI proof points. Medium for production routes until dependency and design-system strategy is settled.

Best Use

Validate rendering and interaction fit first. Full server integration should come after host-app constraints are understood.

Main Risk

Adapters can become a hidden second design system if they are not retired, formalized, or replaced.

Decision Need

Pick a migration host and shared UI/dependency plan before scaling beyond a handful of routes.

Why This POC Exists

The broader initiative is to create a useful unified tool by November. The team is evaluating how to combine capabilities from G2DM, Vendor Portal, and MyG2 without starting a greenfield application.

This POC explores one practical path: move selected Vendor Portal routes into MyG2 Admin and make them work inside the existing Rails application shell. It focuses on feasibility, migration friction, and reusable learnings rather than final production architecture.

Report purpose: help technical stakeholders and migration agents understand what must be inventoried, mocked, adapted, or redesigned when moving a route from one application boundary to another.

Strategy Options

The POC should be read as evidence for one option, not as a final architecture decision.

Option Potential Advantage Main Constraint POC Relevance
Move G2DM/Vendor Portal routes into MyG2 Uses the existing MyG2 Admin host and avoids rebuilding its broad product surface elsewhere. Requires compatibility work for modern Vendor Portal frontend dependencies. This POC directly evaluates this route.
Move MyG2 features into Vendor Portal Uses the newer React application model and modern dependency stack. MyG2 has a large number of routes and mature Rails-backed workflows that would need migration. This remains a comparison path for feasibility and timeline.
Build a greenfield unified app Clean architecture and unified design system from day one. Not realistic under the November timeline. Useful as a reference ideal, but not a practical near-term plan.

POC Scope

In Scope

  • Render the Manage Campaigns UI at https://my.g2.test/g2-seller-solutions/ppc.
  • Mock loader/action responses because data fidelity was not the goal.
  • Bring imported UI components far enough to paint the component tree.
  • Preserve local React interactions: sorting, row actions, modal, toast, and draft deletion.
  • Approximate Vendor Portal styling inside UE without changing global host styles.

Out Of Scope

  • Real server integration or production data contracts.
  • Navigation to unrelated Vendor Portal routes.
  • Full design-system consolidation.
  • Installing the complete Vendor Portal dependency graph into UE.
  • Guaranteeing production accessibility and test coverage for every imported primitive.

Migration Approach Used

The route was mounted from a Rails view through a dedicated Webpack entry named vendor_portal_ppc_entry. The source route shape was preserved where practical, while loader/action behavior was replaced with local mocked data and event handlers.

  • Route hostThe MyG2 endpoint /g2-seller-solutions/ppc became the host for the React mount.
  • Component import strategyLocal POC primitives were created under the UE JavaScript tree to stand in for Vendor Portal UI dependencies.
  • Data strategyServer responses were mocked to prove rendering and interaction behavior without coupling to real backend work.
  • Navigation strategyLinks to other routes were intentionally blocked or converted to local feedback so the POC stayed route-scoped.
  • Styling strategyScoped vp- CSS approximated Vendor Portal tokens while allowing the screen to inherit MyG2 typography where possible.

Findings And Learnings

These are the migration behaviors future agents should account for before opening a code editor.

  • UE can host the experiment. React, TypeScript, and Webpack entries already exist, so a sibling React mount is a viable POC path.
  • The source route assumes React Router. Loader/action/fetcher behavior is a real application boundary, not just a syntax detail.
  • Mocked data removes noise early. It validates UI feasibility before backend integration makes the work harder to evaluate.
  • Component imports expose risk quickly. Missing table, popover, modal, and variant utilities were more important than the table data itself.
  • Typography drift is easy to introduce. The better route was to inherit UE typography and only map the minimum visual differences.
  • Scoped adapters need an exit plan. They worked for the POC, but they should not become permanent by accident.
  • Route-level reports are part of the artifact. Later migrations will repeat the same classes of problems unless each adaptation is captured.

Tailwind And Styling Comparison

Tailwind was the most visible styling mismatch. Vendor Portal class names often encode pixel-level design intent that does not map directly to UE's Tailwind 3 configuration.

Area UE / MyG2 Vendor Portal Practical Impact
Tailwind version ^3.1.8 with JavaScript config and Elevate preset. 4.3.0 with CSS-first @theme static. Directly copying Tailwind classes can produce missing classes or wrong values.
Spacing Custom spacing is split across padding and margin scales. --spacing: 1px, so gap-24 means 24px. Spacing is not portable without a map. This caused much of the local vp- layer.
Typography Figtree is available, but UE typography should generally own the page. Text utilities bundle font size, line height, margin reset, and trim behavior. Recreating Vendor Portal text wrappers caused visible drift. Inheriting UE typography is safer.
Logical utilities Tailwind 3 setup does not expose the same logical-property utility surface. Components use utilities such as inline-24, block-20, and min-block-40. Button, icon, menu, and modal sizing need translation.
Content scanning Main Tailwind globs do not currently cover every TS/TSX path used by the POC. Source is TS/TSX-heavy and assumes its own build pipeline. Using UE Tailwind classes from POC TSX requires content config work or preexisting classes.
Base reset UE already has established global Rails and admin styles. Vendor Portal base rules include broad resets such as button { all: unset; }. Importing the whole Vendor Portal reset would create broad host-app risk.

Styling recommendation: replace local vp- classes with UE-native utilities only where values are known to match. For spacing, colors, radii, shadows, and component states, create a deliberate token map or use UE-native components.

Next-Step Recommendations For Quality

This POC optimized for speed: prove that Vendor Portal React components can render in MyG2. The next iteration should optimize for production quality, even if it moves more slowly.

  1. Solve dependency-difference risks first. Decide whether UE should upgrade React, support React 19 in an isolated bundle, or require source-route adaptations. Do the same for Tailwind 3 versus Tailwind 4 and TypeScript 4.6 versus newer declaration files.
  2. Move React Router data patterns into a Rails-owned boundary. Loader/action/fetcher behavior should become explicit Rails endpoints, props, or a documented adapter contract rather than mocked local state.
  3. Make the design-system decision before porting more UI. Avoid a separate React-route style layer that diverges from Rails views. Either map Vendor Portal tokens to UE, use UE-native components, or publish shared primitives with clear ownership.
  4. Replace POC shims with owned components. Tables, popovers, dialogs, toasts, and icon buttons need accessibility expectations, tests, and a maintenance owner if they remain in MyG2.
  5. Keep the route inventory, but use it as a quality gate. Inventory route links, data dependencies, UI primitives, icons, tables, modals, and toast behavior before implementation, then mark which items are solved by Rails, UE components, shared packages, or adapters.
  6. Define success beyond rendering. The next route should be judged on data ownership, visual consistency, accessibility behavior, test coverage, and how much temporary compatibility code remains.

Risk Register

Risk Severity Why It Matters Mitigation
React major-version gap High Vendor Portal components are authored against React 19 while UE runs React 17. Decide on upgrade, isolated bundle strategy, or compatibility constraints.
Route framework mismatch High Loader/action/fetcher code is central to Vendor Portal routes but not native to the Rails page. Create a route adapter contract or rewrite data boundaries per migrated route.
Styling drift Medium Tailwind v3/v4 and token differences change spacing, type, color, and sizing semantics. Use a token map and favor UE typography and layout where appropriate.
Adapter layer sprawl Medium POC shims can quietly become a second unowned component library. Require ownership, tests, and a retirement plan for every adapter.
Timeline pressure Medium The November target rewards route-by-route progress but can hide systemic debt. Use this report format to force dependency, style, and integration decisions early.

Production Readiness Checklist

A future route should not graduate from POC to production until these items are answered.

  • Dependency plan approved for React, router, table, popover, modal, toast, and variant utilities.
  • Server data contracts implemented or intentionally adapted to the destination app.
  • Route navigation behavior defined for links outside the migrated surface.
  • Styling token map completed for spacing, typography, color, radius, shadow, and interaction states.
  • Accessibility behavior verified for menus, dialogs, keyboard focus, and status feedback.
  • Tests added for critical interactions and route-specific state transitions.
  • Ownership assigned for every compatibility primitive that remains in the destination app.
  • Report updated with final deviations from the source route.
