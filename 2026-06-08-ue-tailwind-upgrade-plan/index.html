UE Tailwind upgrade plan

Move to Tailwind v4 iteratively, with v3 unification first

The safest path is to align UE main Tailwind, UE's embedded Elevate workspace, and the standalone Elevate package on the latest Tailwind v3 line first, then evaluate Tailwind v4 from a stable baseline while touching as little of Nessy, Foundation, Sass, and existing load order as possible.

Summary

This plan turns the styling-landscape research into an implementation sequence for ue-unify-tailwind-3 and the follow-up v4 work. Phase 1 is now implemented, validated, and in review as Draft PR #40142; the standalone @g2crowd/elevate package alignment is now in review as Draft PR g2crowd/elevate-g2#50 under DMVPC-1837.

First Move

Upgrade the UE Tailwind surfaces and the standalone Elevate package to latest v3, currently 3.4.19, without changing the surrounding styling architecture.

Why First

Main UE started on ^3.1.8. UE's embedded Elevate workspace and the standalone elevate-g2/ checkout started on ^3.4.10. Aligning all of them removes version drift before introducing Tailwind v4's larger build-model changes.

Migration Shape

Keep the current Sass, Gulp, PostCSS, Foundation, Nessy, and Elevate asset boundaries intact during the v3 unification PR.

v4 Constraint

Tailwind v4 should be introduced only after the v3 baseline is stable and the team chooses between Elevate-first, scoped bundle, or direct main UE upgrade.

Tailwind v3 Unification Approach

Unification means both Yarn workspaces resolve the same Tailwind package version. It does not mean merging the main UE and Elevate configs, CSS entrypoints, or generated bundles.

Implemented locally: Phase 1 pins root UE and UE's embedded Elevate workspace to exact 3.4.19 for a deterministic review. The standalone elevate-g2/ package now follows the same exact baseline on a separate package branch under DMVPC-1837; Draft PR g2crowd/elevate-g2#50 is open for review.

Step Action Reason
1 Change root package.json from tailwindcss: ^3.1.8 to tailwindcss: 3.4.19. This upgrades the main nessy_app Tailwind generator without touching Sass, Gulp, PostCSS, Foundation, or Nessy source structure.
2 Change engines/elevate/package.json from tailwindcss: ^3.4.10 to tailwindcss: 3.4.19. This keeps Elevate on the same v3 patch while preserving its separate Rsbuild/PostCSS pipeline and elv- prefixed preset.
3 Run yarn install from the UE root and confirm yarn why tailwindcss reports 3.4.19 for both @g2crowd/ue and elevate. The lockfile is the actual proof that the two current Tailwind versions have been unified.
4 Do not add a shared Tailwind config, shared preset, or package resolutions unless Yarn still resolves duplicate Tailwind versions after the direct dependency update. Keeping the change to dependency alignment reduces blast radius and avoids creating an architecture migration inside the version-unification PR.
5 Rebuild and compare nessy_app.css, vendor_admin_assets.css, and Elevate application.css. Both bundles can be loaded on shared routes, so generated CSS output matters even when source files do not change.
6 Relate the standalone elevate-g2/ package Tailwind alignment to DMVPC-1837 and ship it as a separate repo PR before v4 work starts. The UE monorepo change does not update the sibling package checkout that provides @g2crowd/elevate assets.

Migration Principles

  • Touch the styling stack as little as possible. The v3 unification PR should not refactor Nessy, Foundation, Sass partials, asset loading, or CSS architecture unless a Tailwind v3 compatibility issue forces a local change.
  • Separate version alignment from v4 migration. Tailwind 3.4.19 should land as its own reviewable change before any Tailwind v4 package or pipeline work.
  • Keep main UE and Elevate distinct. The first goal is version parity, not collapsing Tailwind configs, prefixes, or asset entrypoints.
  • Prefer evidence over broad assumptions. Each phase should have build output, smoke routes, and a narrow regression read before moving to the next phase.

Validation Gates

These checks keep the v3 work narrow and make v4 safer by exposing problems earlier.

Gate Command or Evidence Why It Matters
