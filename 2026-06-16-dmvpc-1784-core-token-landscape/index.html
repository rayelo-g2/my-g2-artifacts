Core UI Component Token Landscape for DMVPC-1784

A migration-readiness investigation for moving G2DM Vendor Portal React core components into UE, with UE consuming Elevate 2.0 on Tailwind v4.

Summary

Recommendation: use Elevate 2.0/Tailwind v4 as the reusable token source for the UE migration, and turn re-elevate into a short-lived migration workbench rather than a second token API.

The Vendor Portal core component tree can be inventoried and moved, and the Tailwind version mismatch is no longer the central risk. Vendor Portal and UE's embedded Elevate surface are both Tailwind v4-shaped. The remaining risk is token semantics: Vendor Portal still carries G2DM names, pixel-style aliases, logical sizing utilities, custom text utilities, and generated icon assumptions that should not be treated as the final UE API.

The practical migration path is therefore not "copy the Vendor Portal theme into UE." It is to extend Elevate 2.x where reusable token gaps exist, expose the right Tailwind v4 sources for the React migration location, create a small compatibility strategy for the first route/component scope, then rewrite migrated React components toward Elevate semantics. Compatibility aliases can help the first migration land, but they should be treated as a bridge with an expiration plan.

61 Vendor Portal core component dirs

Source and re-elevate currently have the same top-level component count.

38 Elevate package CSS component families

Several core primitives overlap, but React behavior and APIs still need migration decisions.

41 UE Elevate component dirs

UE consumes @g2crowd/elevate 2.0.0 with Tailwind v4 in the Elevate engine.

High-confidence findings

  • Spacing, shadows, and borders are mostly covered by Elevate's 4px scale, numeric shadow levels, border widths, and radius scale. The migration work is mainly naming and class rewriting.
  • Colors are the largest design-system gap because G2DM names such as brand-blue, gray-5, steel, and link-blue need UX-approved Elevate pairings, not just mechanical hex copying.
  • Typography needs semantic aliases if the UX foundation names are expected to survive in code. Elevate has raw type scale values, but the migration needs names such as heading-lg, body-sm, and label-xs.
  • Icons should be scoped by actual migration routes. Vendor Portal has hundreds of generated icon components, while Jira lists a narrower missing-icon set. Full parity is probably wasteful before route scope is locked.
  • The new Tailwind v4 integration still needs React source coverage. UE uses @source for Elevate Rails component/view paths, but the future migrated React/TSX location must be added deliberately.
  • UE root Tailwind should still not become the new token home. The root app keeps legacy Tailwind v3 assumptions; the reusable migration token path should go through Elevate 2.x first.

Foundation Findings

Spacing

Status Finding Needed decision
Mostly covered Vendor Portal currently uses a 1px Tailwind v4 base (--spacing: 1px) and aliases such as p-24px, gap-8px, inline-400, and min-block-420. Elevate 2.0 uses a 4px grid where key 6 maps to 24px, exposed in the prefixed v4 form when used as an Elevate utility. Rewrite to Elevate scale names where possible, for example 24px spacing should become the Elevate 4pt scale token rather than a copied 24px alias. Decide whether temporary aliases such as p-24px are allowed during migration, and whether logical inline-*/block-* utilities belong in Elevate 2.x or stay local to the React migration layer.

Colors

Status Finding Needed decision
Largest gap Vendor Portal uses G2DM names such as brand-blue, brand-blue-1..11, link-blue, gray-1..11, steel, tangerine, and sky. Elevate primitives and semantics are organized around rorange, purple, neutral, blue, green, yellow, plus --elv-bg-*, --elv-text-*, and --elv-border-*. Use UX's color-pairing/tone-scale Figma foundations to approve the exact mappings. Avoid pretending every G2DM color has a perfect equivalent. Prefer semantic Elevate usage for final component code, with explicit compatibility aliases only when needed to land scoped migration work.

Typography

Status Finding Needed decision
Alias gap Vendor Portal relies on text-size-* utilities that bundle size, line-height, margin reset, and text-box trim. Elevate has Figtree and raw font-size/line-height scales, but not an obvious public semantic API for every UX foundation name. Add or document semantic type aliases such as heading-lg, heading-md, heading-sm, body-lg, body-sm-bold, label-sm, body-xs, and label-xs. Confirm whether text-box trim is required in UE or should be dropped.

Shadows

Status Finding Needed decision
Covered Jira maps small, medium, and large shadows to elevation-1, elevation-2, and elevation-3. Elevate 2.0 already has numeric shadow levels and directional variants. re-elevate models the semantic names as shadow-elevation-1/2/3. Pick the final class/API spelling for migrated React. The pragmatic default is to use Elevate's existing numeric levels, while adding semantic aliases only if UX wants elevation-* to be a stable public token name.

Borders and Radius

Status Finding Needed decision
Mostly covered Elevate 2.0 already includes useful border widths and radius scale values. Vendor Portal uses pixel aliases such as rounded-2px, rounded-4px, rounded-8px, and rounded-24px, while re-elevate demonstrates possible compatibility mappings. Use Elevate names for final code. Decide whether pixel aliases are temporary migration-only utilities or a supported public token layer.

Z-index, Motion, and Miscellaneous Tokens

Status Finding Needed decision
Needs definition Vendor Portal and re-elevate both have overlay/layer values for drawer, dropdown, overlay, dialog, in-dialog, toast, and tooltip. Elevate 2.0 has component CSS and UE has a motion dependency in the Elevate engine, but there is still no obvious global z-index token contract in the inspected theme variables. Add a small Elevate layering token set before moving Drawer, Modal, Popover, Select/Menu, Tooltip, and Toast together. Motion tokens were not prominent in the inspected foundation subtasks, but the new motion dependency makes it worth deciding whether component motion should be tokenized alongside layers.

Icons

Status Finding Needed decision
Scope-driven Vendor Portal has 307 generated icon TSX files and 306 SVG source files. DMVPC-1834 lists a narrower missing-icon set. A normalized local check found some listed names already covered by Elevate, some covered by general UE assets, and many missing by simple name match. Do a usage-driven icon port for the first migration candidates. Establish naming corrections now: Location replaces Geotag, and Profile should not be ported unless UX reverses that decision.

Component Landscape

The Vendor Portal core library contains 61 top-level component directories. UE embedded Elevate has 41 top-level Rails ViewComponent directories and consumes 38 package CSS component families from Elevate 2.0. That overlap is strong, but the migration target is still React components in UE, so overlap does not automatically mean "done." Each component still needs a decision about API preservation, behavior ownership, accessibility, and whether route-specific state has leaked into the core component.

Component subtasks should not be generated from the 61-dir list alone. DMVPC-1784 asks for one subtask per component required by the first migration candidates. The full list is a landscape; the delivery backlog should be scoped by actual route usage.

Integration Path

  1. Lock the first migration candidates. Use route-level imports/usages to create the component inventory. The prior Manage Campaigns POC is a useful precedent, but the current target routes should be confirmed.
  2. Normalize the UX foundation mappings. Convert Jira/Figma foundation decisions into a token map with source, target, status, and owner. Colors and typography need explicit UX review before engineering hardens names.
  3. Promote stable gaps into Elevate 2.x. Add reusable token definitions and aliases in elevate-g2, not directly in UE root Tailwind. Since UE consumes Elevate 2.0, future token work should become a small 2.x package increment rather than a separate UE-only token layer.
  4. Expose the React migration source path to Tailwind v4. UE currently uses @source for Elevate Rails component/view paths. Once the React component home is chosen, add that path explicitly so Tailwind v4 emits the required Elevate utilities.
  5. Port components by dependency order. Start with low-level primitives such as Text, Icon, Button, inputs, helper text, and layout primitives before composed controls such as Modal, Select, Combobox, DatePicker, Toast, and Table.
  6. Validate in UE's React-in-Rails environment. The migration must render inside MyG2/UE, not only in a standalone Vite app. Keep route data, endpoint calls, authorization, and session behavior outside core UI components.

What to do with re-elevate

re-elevate is valuable because it already demonstrates that the copied core tree can be pointed at an Elevate-like Tailwind v4 token file. That experiment is close to the real target, but it still should not become a second design-system source. Use it to test class rewrites, identify missing tokens, and compare component visual output, then move durable decisions into Elevate 2.x and the UE Elevate engine.

What not to do

  • Do not import Vendor Portal's full Tailwind theme or reset into UE.
  • Do not add one-off token definitions into route-local React CSS unless they are explicitly temporary.
  • Do not use UE root Tailwind legacy spacing/color modules as the long-term API for Elevate React components, even though the Elevate engine itself has moved to Tailwind v4.
  • Do not port the full Vendor Portal icon set before the first-route usage audit proves it is needed.

Refinement Questions

These are the questions I would bring into the refinement session before turning the investigation into implementation tickets.

  1. Which routes are the first migration candidates now? DMVPC-1784 says scope should be driven by first candidates. We should not create component subtasks from the whole core folder unless that is now the desired scope.
  2. Should migrated React components preserve Vendor Portal public APIs? If yes, we need wrapper/adaptor work. If no, route migration can absorb prop/API changes while moving to Elevate semantics.
  3. Where should the React core components live inside UE? Options include a UE webpack package area, an engine-local React surface, or a package-style shared module. This directly affects the Tailwind v4 @source entry that must be added in the Elevate build.
  4. Are compatibility aliases allowed, and for how long? Names like brand-blue, gray-5, text-size-14px, and rounded-4px can lower migration risk but will become debt if they are treated as permanent design-system names. We need to decide whether any aliases belong in Elevate 2.x or only in a temporary migration stylesheet.
  5. What is the source of truth for color pairings? Jira says not every color has an exact match and calls out Jordi. Engineering should not finalize the color token map without that review.
  6. Should typography be semantic in code? If UX expects Heading Md and Body Xs language to be stable, Elevate should expose those names rather than making every component compose raw font sizes and weights.
  7. How much icon parity do we want? Route-scoped porting is leaner. Full Vendor Portal parity gives safety but adds generation/naming/ownership work immediately.
  8. What exact Tailwind v4 source paths need to be added? The timeline question is mostly answered for the Elevate engine. The open question is whether migrated React files live under existing scanned paths or require new @source entries for JS/JSX/TS/TSX.
  9. What visual proof is expected before merge? Options: Storybook in the migrated React surface, Lookbook/engine previews, route screenshots in MyG2, or a combination.
