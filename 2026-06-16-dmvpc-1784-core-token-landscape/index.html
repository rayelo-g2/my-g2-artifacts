Core UI Component Token Landscape for DMVPC-1784

A migration-readiness investigation for moving G2DM Vendor Portal React core components into UE, with UE consuming Elevate 2.0 on Tailwind v4.

Summary

Recommendation: use Elevate 2.0/Tailwind v4 as the reusable token source for the UE migration, and turn re-elevate into a short-lived migration workbench rather than a second token API.

The Vendor Portal core component tree can be inventoried and moved, and the Tailwind version mismatch is no longer the central risk. Vendor Portal and UE's embedded Elevate surface are both Tailwind v4-shaped. The remaining risk is token semantics: Vendor Portal still carries G2DM names, pixel-style aliases, logical sizing utilities, custom text utilities, and generated icon assumptions that should not be treated as the final UE API.

The practical migration path is therefore not "copy the Vendor Portal theme into UE." It is to stage the full core suite inside UE, extend Elevate 2.x where reusable token gaps exist, expose the right Tailwind v4 sources for the React component location, then rewrite migrated components toward Elevate semantics in place. We should not create a Vendor Portal compatibility alias layer; missing values should become durable Elevate token additions when UX confirms them.

61 Vendor Portal core component dirs

Source and re-elevate currently have the same top-level component count.

38 Elevate package CSS component families

Several core primitives overlap, but React behavior and APIs still need migration decisions.

41 UE Elevate component dirs

UE consumes @g2crowd/elevate 2.0.0 with Tailwind v4 in the Elevate engine.

High-confidence findings

  • Spacing, shadows, and borders are mostly covered by Elevate's 4px scale, numeric shadow levels, border widths, and radius scale. The migration work is mainly naming and class rewriting.
  • Colors are the largest design-system gap because G2DM names such as brand-blue, gray-5, steel, and link-blue need UX-approved Elevate pairings, not just mechanical hex copying.
  • Typography needs semantic variants if the UX foundation names are expected to survive in code. Elevate has raw type scale values, but the migration needs names such as heading-lg, body-sm, and label-xs.
  • Icons should be copied intentionally. Vendor Portal has hundreds of generated icon components, while Jira lists a narrower missing-icon set. Start with icons required by the UE-owned core suite and add route-specific icons as imports demand them.
  • The new Tailwind v4 integration still needs React source coverage. UE uses @source for Elevate Rails component/view paths, but the future migrated React/TSX location must be added deliberately.
  • UE root Tailwind should still not become the new token home. The root app keeps legacy Tailwind v3 assumptions; the reusable migration token path should go through Elevate 2.x first.

Foundation Findings

Spacing

Status Finding Direction
Mostly covered Vendor Portal currently uses a 1px Tailwind v4 base (--spacing: 1px) and aliases such as p-24px, gap-8px, inline-400, and min-block-420. Elevate 2.0 uses a 4px grid where key 6 maps to 24px, exposed in the prefixed v4 form when used as an Elevate utility. Rewrite to Elevate scale names wherever possible. If a spacing value or logical utility is missing, add it as a real Elevate token or utility after design-system review rather than preserving the Vendor Portal class name.

Colors

Status Finding Direction
Largest gap Vendor Portal uses G2DM names such as brand-blue, brand-blue-1..11, link-blue, gray-1..11, steel, tangerine, and sky. Elevate primitives and semantics are organized around rorange, purple, neutral, blue, green, yellow, plus --elv-bg-*, --elv-text-*, and --elv-border-*. Use UX's color-pairing/tone-scale Figma foundations to approve the exact mappings. Avoid pretending every G2DM color has a perfect equivalent. Prefer semantic Elevate usage for final component code, and add missing colors only as durable Elevate token additions.

Typography

Status Finding Direction
Alias gap Vendor Portal relies on text-size-* utilities that bundle size, line-height, margin reset, and text-box trim. Elevate has Figtree and raw font-size/line-height scales, but not an obvious public semantic API for every UX foundation name. Use DMVPC-1825 as the source of truth for type mapping. Decide final public Text variant names during the Text component migration, because that component will define the typography API for the rest of the suite.

Shadows

Status Finding Direction
Covered Jira maps small, medium, and large shadows to elevation-1, elevation-2, and elevation-3. Elevate 2.0 already has numeric shadow levels and directional variants. re-elevate models the semantic names as shadow-elevation-1/2/3. Use Elevate's existing numeric levels unless UX wants elevation-* to become a stable public token name. Any missing shadow token should be added to Elevate rather than shimmed locally.

Borders and Radius

Status Finding Direction
Mostly covered Elevate 2.0 already includes useful border widths and radius scale values. Vendor Portal uses pixel-named classes such as rounded-2px, rounded-4px, rounded-8px, and rounded-24px. Use Elevate names for final code. If a radius or border value is missing from Elevate, add it as a design-system token rather than creating a Vendor Portal compatibility class.

Z-index, Motion, and Miscellaneous Tokens

Status Finding Direction
Needs definition Vendor Portal and re-elevate both have overlay/layer values for drawer, dropdown, overlay, dialog, in-dialog, toast, and tooltip. Elevate 2.0 has component CSS and UE has a motion dependency in the Elevate engine, but there is still no obvious global z-index token contract in the inspected theme variables. Add a small Elevate layering token set before moving Drawer, Modal, Popover, Select/Menu, Tooltip, and Toast together. Motion tokens were not prominent in the inspected foundation subtasks, but the new motion dependency makes it worth deciding whether component motion should be tokenized alongside layers.

Icons

Status Finding Direction
Suite-driven Vendor Portal has 307 generated icon TSX files and 306 SVG source files. DMVPC-1834 lists a narrower missing-icon set. A normalized local check found some listed names already covered by Elevate, some covered by general UE assets, and many missing by simple name match. Port icons required by the copied core component suite and the routes that adopt it. Establish naming corrections now: Location replaces Geotag, and Profile should not be ported unless UX reverses that decision.

Integration Path

  1. Create the UE core component home. Pick the destination path for the UE-owned React core suite and make it the import target for migrated Vendor Portal routes.
  2. Copy the full core suite as the starting point. Move/copy the components from re-elevate or Vendor Portal into UE, preserving enough structure to make import switching predictable.
  3. Do not copy the old styling contract. Bring the React components and supporting assets needed for behavior, but do not bring Vendor Portal global CSS, reset, token files, or re-elevate token CSS into UE.
  4. Normalize the UX foundation mappings. Convert Jira/Figma foundation decisions into a token map with source, target, status, and owner. Colors and typography need explicit UX review before engineering hardens names.
  5. Promote stable gaps into Elevate 2.x. Add reusable token definitions in elevate-g2, not directly in UE root Tailwind. Since UE consumes Elevate 2.0, future token work should become a small 2.x package increment rather than a separate UE-only token layer.
  6. Expose the React migration source path to Tailwind v4. UE currently uses @source for Elevate Rails component/view paths. Once the React component home is chosen, add that path explicitly so Tailwind v4 emits the required Elevate utilities.
  7. Migrate styling in place by dependency order. Start with low-level primitives such as Text, Icon, Button, inputs, helper text, and layout primitives before composed controls such as Modal, Select, Combobox, DatePicker, Toast, and Table.
  8. Switch route imports incrementally. As Vendor Portal routes move into UE, replace imports from Vendor Portal core with imports from the UE-owned core suite.
  9. Validate in UE's React-in-Rails environment. The migration must render inside MyG2/UE, not only in a standalone Vite app. Keep route data, endpoint calls, authorization, and session behavior outside core UI components.

What to do with re-elevate

re-elevate is valuable because it already demonstrates that the copied core tree can be pointed at an Elevate-like Tailwind v4 token file. That experiment is close to the real target, but it still should not become a second design-system source. Use it to test class rewrites, identify missing tokens, and compare component visual output, then move durable decisions into Elevate 2.x and the UE Elevate engine.

What not to do

  • Do not import Vendor Portal's full Tailwind theme or reset into UE.
  • Do not add one-off token definitions into route-local React CSS; missing reusable values should be added to Elevate.
  • Do not use UE root Tailwind legacy spacing/color modules as the long-term API for Elevate React components, even though the Elevate engine itself has moved to Tailwind v4.
  • Do not port the full Vendor Portal icon set blindly; start with icons required by the UE-owned core suite and add route-specific icons as route migrations need them.

Refinement Decisions

These decisions were made after reviewing the report and should guide the next implementation tickets.

  1. Core suite location: the UE-owned React core suite should live under ue/webpack/assets/javascripts/unified_seller_experience/core.
  2. API compatibility: preserve Vendor Portal component APIs by default. Change APIs only when they directly expose old styling concepts, such as typography variants on Text.
  3. Import strategy: use the clean unified_seller_experience/core namespace while keeping component folder/export names close to Vendor Portal to reduce route migration churn.
  4. No compatibility aliases: do not create a Vendor Portal token compatibility layer. Components should be restyled directly against Elevate tokens/classes. Missing values should become real Elevate token additions.
  5. Color source of truth: color mappings are owned by UX/Elevate foundations. Engineering should not infer final mappings from Vendor Portal hex values or re-elevate.
  6. Typography: use DMVPC-1825 as the mapping source. Final Text variant names should be decided during the Text component migration.
  7. Icons: start with Icon component infrastructure and one representative icon. Wait for the final UX/Figma SVG list before compiling the final icon set.
  8. Tailwind source coverage: Tailwind v4 should scan ue/webpack/assets/javascripts/unified_seller_experience/core/**/*.{js,jsx,ts,tsx}, the USE stories, and Storybook config as needed.
  9. Visual proof: Storybook is the primary visual proof for core components. Route screenshots are required when migrated routes switch imports to the UE-owned suite.
